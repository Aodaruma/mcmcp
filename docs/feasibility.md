# 実現性と判断

## 判断

**PoCはGOです。** シングルプレイとマルチプレイの両方で動く、特定サーバーに依存しないクライアントMODとして設計できます。

クライアント専用NeoForge MODから、Minecraftの通常入力とクライアントが既に保持している可視状態を扱うことは可能です。MCP Java SDKにもStreamable HTTPのサーバー実装があり、ゲーム外のLLMクライアントとの接続経路も成立します。

最初にローカルワールドと複製インスタンスで安全性を検証し、入力残留や互換性問題を本番プレイへ持ち込まないようにします。マルチプレイで使う際のルール適合性は、通常のクライアントMODと同様に利用者が接続先ごとに判断します。

## 成立する理由

| 領域 | 判定 | 根拠 |
|---|---|---|
| クライアント専用MOD | 高 | NeoForgeは物理クライアント専用のエントリポイントを分離できる |
| 通常入力による操作 | 高 | クライアントtickとKeyMappingを用いて通常の入力経路を使える |
| MCP接続 | 中〜高 | Java SDKにStreamable HTTPがある。ゲーム内への埋め込みと依存衝突はPoCで確認が必要 |
| Simple Voice Chat連携 | 中〜高 | 2.6.22で状態取得と内部setMuted経路を実JAR・公式ソースから確認済み |
| Modpack互換性 | 中〜高 | レンダラーやGUIへ介入しないPoCなら衝突面が小さい |
| マルチプレイ運用 | 条件付き | 接続先ごとのルール、負荷、公平性、アンチチート挙動の確認が必要 |

## 参照タスクから修正した点

元の検討方針は概ね妥当ですが、現在の仕様に合わせて次を変更します。

1. MCP 2026-07-28ではStreamable HTTPのGETストリームとプロトコルセッションが廃止されたため、単一`POST /mcp`を基準にする。
2. 長時間の作業を1回のHTTPリクエストで保持せず、`start_routine`でIDを返し、状態照会と明示的キャンセルを行う。
3. `hold_forward`などの生の入力ツールは通常モードでLLMへ公開しない。許可リスト式ルーチンの内部実装に限定する。
4. Voice Chatの公開APIは`isMuted()`を提供するがsetterはない。2.6.22専用アダプタを隔離し、起動時互換性検査に失敗したら自動化を禁止する。
5. ベースModpackがバージョン固定のため、依存の自動更新を行わない。

## 主な未確定事項

- 現在利用するMCPクライアントと、MCP 2026-07-28の実際の相互運用
- Java SDKと組み込みServletコンテナをshade/relocateしたJARの起動・終了・依存衝突
- 26.2で通常入力を再現する最小APIと、Sodium・アニメーション系MODとの挙動
- Simple Voice Chat 2.6.22内部APIへの依存が将来の更新で壊れた際の検出方法
- 接続先ごとのルール・アンチチートと、適切な作業範囲・連続稼働時間

これらは新しい環境で能動自動化を有効にする前の互換性・安全性検証項目にします。
