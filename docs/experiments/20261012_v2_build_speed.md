# 地図アート施工の速度計測とR22

2026-10-12。利用者が許可したaod-mimoidの隔離Dockerで、R21とR22候補を同じ固定設計図・装備・設定で比較した。通常ゲームは施工担当が所有し、この開発チャットから操作・再起動・差し替えは行っていない。

## 原因と変更

施工担当の通常R20の記録は、1,155床／373命令で2,779.22秒（約2.41秒／床）。隔離R21の32床は58.42秒（約1.83秒／床）だった。環境が違うため、隔離試験の絶対時間を通常サーバーの予測値には使わない。

R21の32床をclientのpre-tick入口で1,168 ticks標本化した。各tickの状態を数えたもので、関数別CPU時間ではない。

| 分類 | ticks | 比率 |
| --- | ---: | ---: |
| 端へ寄る・確定床へ進む入力区間 | 499 | 42.7% |
| 両区間の停止待ち | 320 | 27.4% |
| 照準・前進前の向き合わせ | 80 | 6.8% |
| 設置準備・照合全体 | 193 | 16.5% |
| 設置driver開始・観測待ち等 | 70 | 6.0% |
| script命令間の切替 | 6 | 0.5% |

設置照合全体のうち`CONFIRMING`は33 ticks（全体の2.8%）。毎床色替えでも全体は58.88秒で、同色列との差は小さかった。手持ち選択より、床ごとの移動と停止待ちが支配的だった。

最初の候補では、隣の完成行を支持にした通常設置を床延長より先に試した。しかし通常設置と後退式床延長を交互に行うと、視点反転が増え、32床は115.38秒、色替えは116.04秒、折返し＋松明は119.41秒になった。この候補`product-r22-candidate.jar`は**不採用**。隣接行を使う案全般が不可能という意味ではなく、この単純な優先順変更は遅かったという結果である。

採用候補`product-r22b.jar`では従来の優先順を維持し、床の端で後退入力を離したら、減速中に照準合わせを開始する。実際の設置は従来どおり静止判定と実際の側面hitが揃ってから行う。入力停止位置、しゃがみ、支持・体の境界、設置予測、サーバー確定、取消・予算は変更しない。公開ツール・引数・設定も変更しない。

32床では、端の停止待ちと照準に費やした合計が200→160 ticksへ減った。移動入力区間は499 ticksのまま。記録上96 ticksで減速と照準が重なり、設置処理に入った全標本では水平速度二乗が従来の静止上限0.000025未満だった。

## 同条件比較

| 設計図 | R21 | R22b | 短縮 |
| --- | ---: | ---: | ---: |
| 同色32床、隣に完成行あり | 58.42秒 | 57.15秒 | 2.2% |
| 32床、1床ごとに黒／灰を交替 | 58.88秒 | 57.10秒 | 3.0% |
| 折返し32床＋松明2個 | 67.46秒 | 64.81秒 | 3.9% |
| 隣に完成行のない最初の16床 | 29.36秒 | 28.60秒 | 2.6% |
| バッグ自動補充、黒4＋松明1＋灰4 | 16.92秒 | 16.60秒 | 1.9% |

同色32床のR22b再測定2回は56.96秒・57.03秒で、初回と合わせた平均は57.05秒。完工試験は計7 Actions／187設置、予期しない失敗0回。母数が小さいため、長時間の失敗率を推定する結果とは扱わない。

各完工Actionは指定数を確定し、終端はHP20・接地・READY・実行中Actionなし。全tick標本でもHP20・接地と一定の床高さを確認した。通常の列・色替え・折返しは設計図の全座標を隔離server側の固定fixtureで照合した。補充ケースの松明はActionの確定結果で確認し、固定serverレポートが含むのは床の層までである。

端へ寄る途中の取消は、完成行のある場合・ない場合とも0設置で終了。親予算16 ticksの試験は減速／照準段階で`script_timeout`になり、0設置・target=airを保持した。既に完了した操作の再送はしていない。

さらに、端へ十分寄って照準を終え、設置準備に入った時点でも取消し、0設置・target=airを確認した。取消3回と予算停止1回を合わせ、R22bは全11ケースの期待結果を満たした。実行profileの製品／harness hashと、終了時のsession `c12e641f-f9d8-46e2-8d88-571c8fe25094` を20:56 JSTに照合した。Action IDと各結果は成果物の`evidence/final-verification.json`を参照。

計測スクリプトが、大きいfixture JSONを書込み途中に読んだエラーを1回修正した。既存Actionの成功receiptと書込み済みserver結果から検証を再開し、施工を再実行していない。また親scriptの予算停止理由の期待値を、実装どおり`script_timeout`へ修正した。これらは製品の施工失敗ではない。

- Java自動テスト1,924件（unit1,882／harness14／admin28）、build、harness隔離、source checksが成功。

計測器はopt-inのprivate統合server専用harnessに置き、製品JARへ含めない。1ケース6,000標本を上限にし、同じ計測器で新旧を比較した。`place.IDLE`は開始処理や観測待ち等を含む。pre-tick所要時間はruntime入口全体で、分類した個別関数だけのCPU時間ではない。

今回の改善は小さく、配布時点では通常サーバーでの長時間速度・失敗率は未確認だった。後続の現場結果は下記へ追記する。落下救助・敵・server correctionの全シナリオは再試験せず、これまでの記録と既存自動テストを維持する。R21の松明修正を含むが、通常環境での偶発停止の完全解消とは扱わない。大幅な高速化には、既存行の上を通る経路と連続設置を組み合わせた別の移動設計が必要になる。

隔離環境は20:56 JSTに元66ファイル（world61ファイルを含む）のhash一致で復元した。Docker終了コマンドは応答まで時間がかかったが正常終了し、20:58 JSTにDockerプロセス0、Ubuntu／docker-desktop両WSL停止とlease解放を確認した。強制終了は行っていない。復元と終了の証拠は`evidence/restoration.json`、`evidence/shutdown.json`、`evidence/complete.json`に保存する。
