# 松明の前後で止まって見える時間と台帳処理の高速化

2026-10-14。利用者から、松明の設置付近で数秒待っているように見えるとの報告を受け、視点移動と施工workerの待ちを分けて調べた。通常ゲーム・worker45792・正式台帳・JAR・共通MCPクライアントは変更していない。保存済み公開receiptと現在のworkerを読み取り、隔離コピーで検証した。

## どこに時間がかかっているか

松明の単発設置に加え、通常workerは松明ごとに区間を終え、確定記録を保存し、支持床と松明を観測し、床中央へ移動して状態を再確認してから次の施工を受け付ける。これは従来の松明付近の停止を避ける手順であり、今回も維持する。

直近の保存済みreceiptから、前後の完了ファイルと対応する観測・移動結果が揃う38区間を集計した。手動中断などを含む90秒以上の境界は除外した。

| 区間 | 中央値 |
| --- | ---: |
| 支持確認のobserve/report Action自体 | 0.209秒 |
| 床中央へのmove Action自体 | 2.412秒 |
| 前区間の結果ファイル → 観測結果ファイル | 13.370秒 |
| 観測結果ファイル → 移動結果ファイル | 9.124秒 |
| 移動結果ファイル → 次Action開始の推定時刻 | 7.357秒 |
| 前区間の結果ファイル → 次Action開始の推定時刻 | 30.197秒 |

後ろ4行は保存ファイルのmtimeと次Actionのelapsedから計算した概算で、処理内のストップウォッチ計測ではない。poll応答・保存時間、別の行や時刻の違いも含む。各行の中央値は加算できない。施工台帳の `torch_overhead=33.672秒` もworker全体から床基準を差し引いた残差であり、松明MOD処理単体の性能値ではない。

## 視点移動の影響

通常設置driverは `max_camera_degrees_per_second` を参照する。コード上の既定値は90度/秒（設定範囲15～360度/秒）なので、90度の大きな向き直しなら上限から約1秒かかり得る。今回、稼働中の実設定値は照会していない。

保存済みR22bの「32床＋松明2個」の隔離profileでは、通常設置driverの `FACING=26 ticks` と `FACING_CROUCHED=3 ticks`、`WAIT_SNEAK=2`、`WAIT_CROSSHAIR=2`、`CONFIRMING=2` が記録されている。これはそのfixtureの集計であり、現在の通常ゲームの1本あたりの時間ではない。視点移動は寄与するが、通常workerの約30秒の境界を視点速度だけで説明する証拠はない。

## 実装した候補

約25MBに育った台帳を、workerが毎回すべてPowerShellオブジェクトへ展開し、保存のたびに全件を再変換していた。松明区間ではこの保存を繰り返す。

`tools/build-worker/BuildProgressJson.ps1` を追加し、workerが追記しない確定床・松明の配列を.NETの `JsonElement` として保持する。小さな所有権・進捗・pendingなどだけを従来のPowerShell変換へ渡す。記帳は既存 `record_blueprint.py` に任せ、その後は正式な台帳を読み直す。UTF-8 BOM、深さ100までのJSON、未知の記録フィールドも維持する。

読取りは `FileShare.ReadWrite|Delete` でメモリへコピーし、ファイルを閉じてから解析する。書込みは一時ファイルまでとし、workerの既存lock・所有権チェック・原子的置換と再試行を使う。台帳から記録を削除・省略する変更ではない。metadataのPSCustomObjectと日時の変換も従来どおり。

worker本体の変更はhelperの読込み、Read/Save、配列件数、最後の確定床の取得だけ。以下は従来のまま：

- 支持観測、中央への移動、体力・足場・session・Actionの確認。
- 設計順・hash照合・一度だけ記帳・未確認操作の停止。
- 排他的所有、BUILD-STOP、有限予算、03:00再起動前の余裕。
- 画面・カメラ速度・設置予測・サーバー確定・製品JAR。

## オフライン比較

同じ25,533,424文字の台帳スナップショット（床73,793件・松明798件）を使い、旧方式／候補を交互の順番で4回測定。初回をウォームアップとして除いた3回の中央値：

| 台帳処理 | 旧方式 | 候補 |
| --- | ---: | ---: |
| 読込み・解析 | 2.516秒 | 0.177秒 |
| JSON変換・一時ファイル書込み | 3.413秒 | 0.172秒 |
| 上記1往復 | 6.140秒 | 0.349秒 |

1往復では約94.3％短縮。各列の中央値は加算できない。通常ゲームを継続しているPC上でのコピーの測定なので、負荷の変動は含む。ゲーム操作・通信・Python記帳・設計読込みの時間は含めない。これを松明全体や建築全体の高速化率として使わない。

旧方式と候補の出力JSONをPythonで全項目比較し、73,793床・798松明を含め意味的に完全一致した。JSONのプロパティ順やエスケープの表記は変わる場合がある。

新規6テストが成功：metadata変更・元ファイル置換後も確定配列保持、UTF-8 BOMと深い未知データ、大きな整数、空の確定床、欠損／不正配列、書込み先lock・不正値時に正式台帳を不変に保つことを確認した。初回テストではテスト用PowerShellの作業ディレクトリ設定を修正し、全件再実行している。

さらにゲーム接続関数を必ず例外にする隔離コピーで、旧workerと候補のDryRunを比較した。正常、所有者違い、記帳件数不一致、未確認pending、設計hash違いの5条件×2版＝10件が期待結果に一致。正式・コピー台帳への書込みもゲーム呼出しも0。成功DryRunの所要時間は旧8.865秒／候補4.494秒だったが、1回ずつの起動比較であり本体速度の基準値には使わない。

`tools/check-source.ps1 -SkipJava -PythonExecutable python` も終了コード0で成功し、新規テストを同チェックへ登録した。JavaコードとJARは変更していないため、今回はJava build・ゲーム起動を行っていない。
